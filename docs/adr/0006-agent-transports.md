# ADR 0006. Единый исполнитель для каналов действий

## Контекст

Локальные решения, задачи с участием чата и входящие сообщения из Telegram могут менять один проект. Ответ о постановке действия в очередь ещё не доказывает завершение работы, а два канала не должны создавать двойной платный вызов или конкурирующие записи.

## Решение

Проводить действия через единый журнал и исполнитель с точными идентификаторами проекта, действия и цели, ожидаемой ревизией, ключом идемпотентности и разрешением на действие. Локальный контроллер использует одну аренду рабочей области и адаптеры host-инструментов. Маршрут модели и операции задаётся ограниченной конфигурацией, а не произвольными данными браузера. Осознанный запуск кнопкой генерации после настройки маршрута разрешает один ограниченный запуск; автоматический режим использует заранее утверждённый контекст проекта. Telegram передаёт текст и медиа через тот же контракт исполнителя. Результат показывается только после чтения канонического состояния.

## Почему

Считать постановку в очередь успехом, повторять неизвестный запрос или писать состояние проекта напрямую из браузера нельзя надёжно сверить и легко приводит к дублям. Единый исполнитель сохраняет общие правила авторизации, ревизий и истории для всех каналов.

## Последствия

Неизвестный исход внешнего вызова требует сверки чтением без повторного платного запроса. Выдача разрешения и постановка действия в очередь согласуются атомарно; исходная ревизия сохраняется отдельно от ревизии исполнения. Закрытый чат не считается гарантированно пробуждаемым. Вложения проверяются и остаются невыбранными, пока не определён проект.
